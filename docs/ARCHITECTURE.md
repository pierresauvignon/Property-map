# Property Map — architecture

A shared property shortlist for two people (Alex, Sam). Static SPA on
CloudFront, one Lambda behind the same distribution, one DynamoDB table.

Region and names come from `infra/config.sh` (see `config.example.sh`).
Cost for a household's use: well under $1/month, mostly S3 storage.

## Naming

Every resource is named from `NAME` and `BUCKET_PREFIX` in the config
(`infra/lib.sh` derives the rest), so several installs can share an account.

| Resource | Name |
|---|---|
| DynamoDB table | `$NAME` |
| Lambda | `$NAME-api` |
| Lambda role | `$NAME-api-role` |
| Site bucket | `$BUCKET_PREFIX-web` |
| Upload bucket | `$BUCKET_PREFIX-uploads` |
| CloudFront | comment `$NAME`, alias `$DOMAIN` if set |
| ACM cert | `$DOMAIN` (us-east-1, DNS validation), only if `DOMAIN` is set |

## Routing

One CloudFront distribution, three origins. This keeps the API same-origin, so
the auth cookie is a plain first-party `HttpOnly` cookie and there is no CORS.

```
/           -> S3 site bucket      (OAC, private bucket)
/api/*      -> Lambda Function URL (auth NONE + origin secret, see below)
/photos/*   -> S3 uploads bucket   (OAC, security headers)
/files/*    -> S3 uploads bucket   (OAC, security headers)
```

**Why the Function URL is public.** CloudFront's Origin Access Control does not
sign request bodies, so with `AuthType AWS_IAM` every POST and PUT fails with
403. Instead the URL is `AuthType NONE`, CloudFront adds an `x-origin-secret`
header to every request it forwards, and the Lambda rejects anything without
it. The secret is generated by `provision.sh` into `infra/.origin-secret`
(gitignored). There are deliberately no 403/404 → `index.html` error mappings:
they turn API failures into a 200 page of HTML, which is miserable to debug.

`/api/*` cache policy: **CachingDisabled**, forward all cookies, all methods.

## Data model — single table `PropertyMap`

`pk` (S, hash), `sk` (S, range). On-demand billing. TTL attribute `ttl`.

| Item | pk | sk | Attributes |
|---|---|---|---|
| Property | `PROP#<id>` | `META` | name, address, town, kind, lat, lng, price, surface, rooms, chambres, terrain, type, photo, street, url, links (other agencies' adverts for the same house), note (free text), listing, geo, dpe, ges, spot, visits (`[{at, by}]`: every time one of us goes round, `at` local `YYYY-MM-DD[THH:mm]`, `by` `alex` or `sam`), sold, editedBy, editedAt |
| Score | `PROP#<id>` | `SCORE#<user>` | value 0..5 in half steps, updatedAt |
| Note | `PROP#<id>` | `NOTE#<ts>#<user>` | user, text, createdAt, reactions (`{"👍": [user, …]}`) |
| Photo | `PROP#<id>` | `PHOTO#<ts>` | user, key, url, contentType, size (videos only), createdAt, notified |
| File | `PROP#<id>` | `FILE#<ts>` | user, key, url, name, size, contentType, createdAt, notified |
| Session | `SESS#<token>` | `SESS` | user, createdAt, ttl |
| User | `USER#<id>` | `USER` | name, passHash (sha256 of salt+pwd) |

Three logins: `alex` and `sam` keep the record, `guest` is read-only. A
read-only account may GET everything and POST comments, photos and documents;
every other mutating route answers 403 (`READ_ONLY_USERS` in `api/index.mjs`).
Add or re-password one with
`node api/add-user.mjs <id> "<name>" <password> [--force]`. The ids are fixed
in three places that must agree: `VALID_USERS` in `api/index.mjs`, `USERS` in
`web/app.js` (and `extension/content.js`), and the login buttons in
`web/index.html`.

`kind` is `"property"` or `"land"` — derived on seed from `type`
(`Terrain` -> land) and correctable by either user.
`town` is derived from the address postcode/commune and is a filter facet.

`spot` is the Emplacement mark, 0..5 in half steps — the one rating that is a property
attribute rather than a `SCORE#` row, because the spot does not depend on who
is looking. Either user sets it and it stands for both.

`sold` is a boolean: the house went to someone else. Unlike `hidden` it does not
remove the property from any list — it stays on the map and in the table, muted
and badged *vendu*, because what a street actually sold for is the comparison
you want later. Set from the property panel; read-only accounts cannot set it.

## API — all JSON, all under `/api`

Auth cookie: `pm_s=<token>`, `HttpOnly; Secure; SameSite=Lax; Path=/;
Max-Age=7776000` (90 days). Every route except `/api/login` requires it and
returns 401 without it.

| Method | Path | Body | Returns |
|---|---|---|---|
| POST | `/api/login` | `{user, password}` | `{user}` + Set-Cookie |
| POST | `/api/logout` | — | `{ok:true}`, clears cookie |
| GET | `/api/me` | — | `{user}` |
| GET | `/api/data` | — | `{properties:[...], scores:{}, notes:{}, photos:{}, files:{}, rev}` — the whole dataset in one call |
| PUT | `/api/property/:id` | partial fields | updated property |
| PUT | `/api/score/:id` | `{value}` 0..5, null clears | `{ok}` |
| POST | `/api/note/:id` | `{text}` | created note |
| DELETE | `/api/note/:id/:ts` | — | `{ok}` (own notes only) |
| PUT | `/api/note/:id/:ts/react` | `{emoji, on}` | `{reactions}` — sets (not toggles) the caller's reaction; a new one mails the comment's author |
| POST | `/api/upload/:id` | `{contentType, size}` | `{putUrl, url, key, ts, contentType}` presigned PUT (photos and videos; `size` required for a video) |
| POST | `/api/file/:id` | `{name, contentType, size}` | `{putUrl, url, key, name, size, contentType, ts}` presigned PUT (documents) |
| DELETE | `/api/file/:id/:ts` | — | `{ok}` — removes the row and the S3 object |
| POST | `/api/notify-files/:id` | — | `{ok, sent, files, photos, videos}` — one email for a whole batch |
| DELETE | `/api/photo/:id/:ts` | — | `{ok}` — removes an uploaded photo, row and object |
| POST | `/api/property` | full fields | created property |

`GET /api/data` returns everything (a hundred properties is a few hundred KB)
so the client can work entirely from one cached payload.

Uploads never stream through the Lambda: it signs a five-minute PUT and the
browser sends the bytes straight to the uploads bucket, which CloudFront
serves back under `/photos/*` and `/files/*`. Photos are capped by type only;
videos (MP4, MOV, WebM) share the photo route and rows, capped at 500 MB;
documents are capped at 25 MB and to the types in `ALLOWED_FILE_TYPES`. A
document's original filename lives in DynamoDB, never in the S3 key, so keys
stay ASCII and collision-free while an accented name survives intact.

## Offline / poor connectivity

- Service worker: app shell precached, cache-first. `/api/data`
  network-first, falling back to the cached copy when offline or after 4 s.
  (Stale-while-revalidate made every launch show the previous launch's data.)
- The client refetches `/api/data` when it returns to the foreground and
  every 60 s while visible, skips the repaint when nothing changed or when
  something is in progress (typing, a dialog, an upload, queued writes), and
  rebuilds an open panel in place at its scroll position.
- A new service worker (`V` bumped in `sw.js`) reloads the page as soon as
  nothing is in progress, or when it next goes to the background, so a
  deploy reaches an already-open app without a manual hard refresh.
- Writes (score, note, edit) go to an IndexedDB outbox and replay on
  reconnect; the UI updates optimistically and shows a pending marker.
- Photos are `<img loading="lazy">` with explicit dimensions; hero images are
  proxied through CloudFront where possible.

## Auth notes

Passwords never reach client code: the client posts one, the Lambda compares a
salted SHA-256 against the `USER#` item, and only an opaque session token
reaches the browser. `api/seed.mjs` gives each login a random password and
prints it once; no password ships with the code.

Short passwords are tolerable only because of the lockout: every 5 wrong codes lock that login
(`LOCK#<id>` item), 15 min the first time and doubling up to a day, and the
count only resets on a successful sign-in. A successful login deletes the item.

## One email per batch of uploads

`POST /api/notify-files/:id` is called by the client once its upload queue has
drained, not once per file. It takes no list: it looks up the caller's own
`FILE#`/`PHOTO#` rows for that property created in the last 15 minutes that are
not yet marked `notified`, stamps them, and sends a single email naming the
documents and counting the photos.

Taking no list is what makes it safe. The call is idempotent, so a retry from
the offline outbox sends nothing; a batch the browser abandoned is swept into
the next email rather than lost; and it can only ever name rows that already
exist and belong to the caller, so it cannot be used to send arbitrary mail.

## Two kinds of photo

`d.gallery` holds the listing's own pictures, mirrored into S3 from the portal.
`PHOTO#` rows hold what we uploaded ourselves. They live under the same
`/photos/` prefix, which makes them easy to confuse, but they are used in
different places on purpose:

- **The listing gallery** is the property's face: the panel carousel, the card
  thumbnail, the map marker and the browse deck, falling back to the stored
  hero and then Street View.
- **Uploads** appear only in the Photos section of the panel, with their own
  full-screen viewer and a delete control. A screenshot of a map is a useful
  note to each other, not a picture of the house, so it stands in for one only
  when the listing has nothing at all — no gallery, hero or Street View.
  **Videos** are uploads too — a `PHOTO#` row whose `contentType` is
  `video/*` — and only ever appear here, never as a stand-in. The service
  worker leaves them to the network: players fetch byte ranges, which a cached
  200 cannot answer, and one would evict hundreds of map tiles. Their stale-row
  sweep and email window are an hour, not five and fifteen minutes, since a
  long upload's row is stamped when the PUT starts.

Both open in the same viewer component; `openLightbox(d, at, mode)` takes
`'listing'` or `'uploads'` and that choice decides both the source and what the
delete button removes.

The `ts` returned by `POST /api/upload/:id` is the row's sort key. The client
must store that value rather than its own clock, or the later
`DELETE /api/photo/:id/:ts` addresses a row that does not exist and silently
does nothing.

## The energy letters

`dpe` (consumption) and `ges` (emissions) each hold a single letter `A`–`G`, or
are absent. The API validates them against `^[A-G]$` and takes `null` to mean
"clear it"; land has neither, and neither does a listing that predates the 2021
format.

Where they come from, in order of reliability:

1. **The bookmarklet**, on the page you are looking at. SeLoger renders each
   diagnostic as an `h3` sharing a parent with a
   `[data-testid="cdp-preview-scale-highlighted"]` badge; BellesDemeures marks
   the active box with a `dpeX`/`gesX` class alongside `diagnosticBoxActive`;
   Leboncoin puts `energy_rate` and `ges` in `__NEXT_DATA__`.
2. **By hand**, from the two selects in *Compléter la fiche* — which is the only
   route for the half of the list with no live listing left.

Two traps worth remembering if this is ever re-run. Some SeLoger listings are
server-rendered and some are not: on a client-rendered one there is no `h3` at
all and the letters exist only in an embedded JSON blob, where the rating sits
just *before* the diagnostic's `"name"`. And a fetch of a dead listing can
return **200 with a "Annonce supprimée" page** rather than 410, so status code
alone does not tell you whether a listing is alive.

## Colouring the map

`state.shade` is `'ppm'` or `'dpe'`, remembered in `localStorage` under
`pm-shade` and switched from the legend. `shadeOf(d)` returns the CSS class
for the current mode, or `null` when the property cannot be placed on that axis
— no surface in price mode, no rating in DPE mode. Callers decide how to draw
that: chips use `chip--none`, map thumbnails use `b0`. The DPE scale is declared
once as `--dpe`/`--dpe-on` custom properties on `.dpe-a` … `.dpe-g`, so chips,
map pins, the legend ramp and the panel badges all read from the same source.
